# 국내 단타 실거래 매커니즘 상세 문서

## 1. 전체 흐름

이 시스템은 `학습/추천`과 `실거래 실행`을 분리한다.

1. `daytrade.py`
   - 과거 분봉 데이터를 준비한다.
   - 전략별 파라미터를 백테스트한다.
   - 추천 종목과 전략을 고른다.
2. `daytrade_engine.py`
   - 현재 시점 분봉 + 현재가를 가져온다.
   - 상태 파일(`data/daytrade/live_state.json`)을 읽는다.
   - 현재 포지션, 평단가, 당일 손익, 수동 상단가/손절가, 예약 매도 상태를 반영한다.
   - 현재 액션을 `BUY1`, `BUY2`, `SELL_FULL`, `SELL_RECENT`, `SELL_RESCUE`, `SELL_STOP_LOSS`, `SELL_MANUAL`, `PRE_SELL_JACKPOT`, `HOLD` 중 하나로 결정한다.
3. `api.py`
   - UI 요청을 받아 추천/학습/실행/상태 조회를 중계한다.
4. UI (`view.ts` / `view.pug`)
   - 추천 결과, 예산, 현재 시그널, 실시간 상태, 거래 일지를 보여준다.

---

## 2. 상태 저장 구조

실거래 엔진은 종목별 상태를 `data/daytrade/live_state.json`에 저장한다.

주요 필드:

- `symbol`, `market`, `name`
- `strategy_id`
- `seed`
- `buy1_used`, `buy2_used`
- `position_qty`
- `avg_price`
- `realized_profit`
- `manual_sell_enabled`, `manual_sell_target_price`
- `stop_loss_enabled`, `stop_loss_price`
- `pending_sell_order_no`, `pending_sell_price`, `pending_sell_qty`
- `orders` (최근 주문 이력)
- `last_signal`, `last_exit_action`, `last_exit_reason`

즉, 이 엔진은 "브로커 계좌 상태"와 "엔진 내부 상태"를 같이 본다. 내부 상태만 믿지 않고, KIS 보유 수량도 주기적으로 동기화한다.

---

## 3. 예산 계산

실거래 예산은 `daytrade_engine.py`의 `shared_budget_status()`가 계산한다.

### 3.1 잔고 원천

1. 1순위: KIS 주문가능금액 조회
   - `TTTC8908R`
   - `ord_psbl_cash`
   - 실제로 지금 신규 매수 가능한 금액
2. 2순위: 국내 잔고 조회
   - `TTTC8434R`
   - 표시용 예수금, 당일 매수/매도 금액 보완

### 3.2 핵심 원칙

- 단타 실매수 가능 금액은 `withdrawable_krw` 기준이다.
- 당일 매도 대금은 `TTTC8908R`에 이미 반영되므로 중복 가산하지 않는다.
- 무한매수 예약금 무시 옵션이 켜져 있으면 예약금을 차감하지 않는다.
- 캐시 미스일 때 UI는 0으로 빠르게 응답하고, 워커 또는 수동 실행이 캐시를 채운다.

## 4. 매수 시그널 생성

`signal_status()`는 내부적으로 `_signal_from_state()`를 호출한다.

### 4.1 데이터 준비

- 최신 1분봉 스냅샷 로드
- 현재가 반영
- 전략 프로필 로드
- 상태 파일 로드
- 브로커 보유 수량 동기화

### 4.2 전략별 진입 규칙

#### V-REV 역추세
- 기준가: 전일 종가 `anchor`
- `BUY1`: 현재가가 1차 눌림 구간 이하
- `BUY2`: 현재가가 2차 눌림 구간 이하
- 각 단계는 당일 한 번만 사용

#### 이동평균 추세추종
- `ma_fast > ma_slow > ma_trend`
- `MACD histogram > 0`
- 거래량 증가
- VWAP 위에서 가격 유지

#### RSI 평균회귀
- RSI 과매도
- 시가 대비 음의 괴리 확대
- 반등 구간 진입

#### 거래량 돌파
- 거래량 급증
- 최근 고점 돌파
- VWAP 위 유지

### 4.3 주문 수량

`_buy_qty()`가 예산과 현재가를 기준으로 매수 수량을 계산한다.

즉, 시그널은 "진입할지"만 결정하고, 실제 수량은 예산/현재가/보유 상태를 반영해 별도로 계산한다.

## 5. 매도 시그널 생성

포지션이 있을 때는 아래 우선순위로 매도 조건을 평가한다.

### 5.1 예약 매도 동기화 우선

`_sync_pending_sell()`가 먼저 실행된다.

- 이미 예약 매도 주문이 있으면
  - 체결 여부 확인
  - 부분 체결 여부 확인
  - 가격이 예약가에서 1% 이상 이탈했는지 확인
- 이탈 시 취소
- 체결 시 상태 갱신

즉, 예약 매도가 걸려 있으면 일반 매도 시그널보다 우선한다.

### 5.2 강제 청산 우선순위

1. 사용자 지정 손절가 이탈 → `SELL_STOP_LOSS`
2. 자동 손절가 이탈 → `SELL_STOP_LOSS`
3. 사용자 지정 상단가 도달 → `SELL_MANUAL`

### 5.3 전략 청산 우선순위

#### V-REV
- 잭팟 수익률 도달 → `SELL_FULL`
- 볼린저 상단 도달 → `SELL_FULL`
- RSI 과매수 진입 → `SELL_FULL`
- 잭팟가 0.5% 이내 진입 → `PRE_SELL_JACKPOT`
- 최근 레이어 복구 구간 → `SELL_RECENT`
- 2차 매수 후 구조 복구 → `SELL_RESCUE`

#### 이동평균 추세추종
- 목표 수익률 도달
- 추세 꺾임
- MACD 약화

#### RSI 평균회귀
- RSI 회복
- 단기 목표 수익률 도달
- 중기 평균 회복

#### 거래량 돌파
- 목표 수익률 도달
- 돌파 실패
- VWAP 하향 이탈

---

## 6. 수수료 손익분기 필터

매도 신호가 나와도 바로 팔지 않는다.

### 6.1 이유

소폭 수익 구간에서 팔면 실제로는 수수료와 거래세 때문에 손실이 될 수 있다.

### 6.2 계산

- 매수 수수료: 0.015%
- 매도 수수료 + 거래세: 약 0.195%
- 손익분기 기준: 대략 평균단가의 `1.0021배`

### 6.3 동작

- `SELL_*` 신호라도 손절이 아닌 경우
- 현재가가 손익분기 미만이면
- 액션을 다시 `HOLD`로 바꾼다

즉, "팔 수는 있지만 팔면 손해"인 상황을 자동으로 막는다.

---

## 7. 사전 예약 매도

이 시스템의 핵심 차별점 중 하나다.

### 7.1 발동 조건

- 포지션 보유 중
- V-REV 전략
- 현재가가 잭팟 목표가 0.5% 이내 접근
- 아직 예약 주문 없음

### 7.2 실행 내용

- `PRE_SELL_JACKPOT` 액션 생성
- 잭팟가 기준 지정가 매도 주문 제출
- 주문번호와 가격을 상태 파일에 저장

### 7.3 이후 관리

- `_sync_pending_sell()`가 체결 여부를 감시
- 가격이 예약가에서 크게 멀어지면 자동 취소
- 체결되면 실현손익, 보유수량, 평균단가 갱신

즉, 목표가 도달 직전부터 체결 우위를 선점하려는 구조다.

---

## 8. 실제 주문 실행

실제 주문은 KIS API를 사용한다.

### 8.1 매수
- 시장가 또는 지정가 주문 전송
- 주문 성공 시 `orders` 이력 저장
- 상태 파일 갱신
- 실행 로그/런타임 로그 기록

### 8.2 매도
- 시장가/지정가 주문 전송
- 평균단가 기준 실현손익 계산
- 수량 차감
- 0주가 되면 평균단가 초기화
- 최근 매도 사유/주문번호 저장
- 거래 로그 저장

### 8.3 수동 즉시 매도
- `manual_sell()` 호출
- 현재 보유 수량 확인
- 즉시 시장가 매도
- 로그에 순손익까지 남김

로그에는 다음 정보가 기록된다.

- 평단 → 매도가
- 총 손익
- 수수료
- 순손익

## 9. 자동 손절 / 수동 상단가 감시

이 시스템의 상단가/손절가는 브로커 서버에 예약을 걸어두는 방식이 아니라, 엔진이 주기적으로 감시하는 방식이다.

`_exit_watch_payload()` 기준:

- `manual_sell_enabled=true` 이고 상단가 존재 → 상단가 감시
- `stop_loss_enabled=true` 이고 손절가 존재 → 손절 감시

메시지에도 명시되어 있듯이:

- 브로커 서버 예약주문이 아니라
- 스케줄러 감시형 자동청산

즉, 엔진이 살아 있어야 감시가 동작한다.

## 10. 위험 제어

`_guardrails()`가 주문 전 최종 안전장치를 담당한다.

주요 검사 항목:

- KIS 연결 상태
- 실전/모의 여부
- 주문 금액이 허용 예산 초과인지
- 현재 단타 사용 중 자금이 포트폴리오 한도를 넘는지
- 일일 손실 제한 도달 여부

결과:

- `SAFE`
- `WARN`
- `HALT`

`HALT`이면 신규 매수는 막는다. 단, 청산은 허용할 수 있다.

---

## 11. 자동매매 워커

워커는 `Struct`에서 백그라운드 스레드로 유지된다.

역할:

- 주기적으로 `auto_cycle()` 또는 관련 점검 실행
- 잔고 캐시 채우기
- 시그널 생성
- 자동매매 조건 충족 시 주문 실행
- 최근 결과를 `worker_status()`로 노출

중복 생성 방지를 위해 스레드 이름을 기준으로 한 번만 뜨도록 막아두었다.

---

## 12. 실거래에서 중요한 해석

이 시스템은 단순히 "가격이 오르면 매도"가 아니다.

실제 흐름은 아래와 같다.

1. 예산이 실제 주문 가능 금액인지 확인
2. 상태 파일과 브로커 보유 수량을 동기화
3. 현재 1분봉과 현재가로 신호 계산
4. 손절/상단가/예약매도 여부 우선 확인
5. 전략 청산 규칙 확인
6. 수수료 손익분기 필터 적용
7. 위험 제어 검사
8. 실제 주문 전송
9. 주문/체결/실현손익/일지 기록

즉, 매수보다 매도가 더 복잡하며, 특히 아래 네 가지가 핵심이다.

- 예약 매도 감시
- 수수료 손익분기 방어
- 자동 손절/수동 상단가 감시
- 브로커 잔고 동기화

---

## 13. 현재 운영 상 주의점

- UI의 `live_status`는 빠른 응답을 위해 캐시 위주로 동작한다.
- 실제 잔고는 워커 실행 또는 수동 auto cycle 이후 가장 정확하다.
- 장중 데이터 준비가 늦으면 `is_loading=true`로 응답할 수 있다.
- 학습 후보가 모두 실패하면 추천은 기존 기본 종목 유지로 폴백한다.
- 개별 학습 실패 종목은 오류 대신 제외 처리한다.
